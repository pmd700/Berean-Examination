“Here is the missing context for the non-API translations in this app. ESV/NLT/KJV are handled separately, but BSB, NASB1995, and LSV are intended to come from source text files that the user uploads, not from API keys. Right now the app is still treating at least some of those translations like remote/API-backed sources, which is why the UI says things like ‘BSB is not available via API.’ I need you to refactor that flow so uploaded translation files become the source of truth for those versions.

Treat uploaded files for BSB, NASB1995, and LSV as importable translation datasets, not ad hoc pasted chapter text.
Build or verify a persistent server-side ingestion process that reads the uploaded text files, parses them into a structured format, and stores them in a queryable local datastore/entity keyed by translation + book + chapter.
The frontend chapter loader for these file-backed translations must no longer call an API expecting a third-party upstream response. Instead, it should query the locally imported translation data and return the matching chapter text.
If the user uploads all three translation files at once, the ingestion flow must identify which file belongs to which translation, parse each independently, and save them without collisions.
If file naming is ambiguous, add a lightweight mapping step so the user or admin can assign a file to BSB, NASB1995, or LSV before import.

If a StudyChapter already exists for a given translation/book/chapter but has empty raw_text, and imported source text is now available, update that existing record rather than leaving it broken.
Preserve the current UX where the user selects a Bible version, book, and chapter. But for file-backed versions, the fetch logic should resolve against imported text data rather than external APIs.
Add clear diagnostics/logging for: file received, translation detected, parse success/failure, chapters imported count, and per-chapter lookup misses.
Add user-facing errors that distinguish between:
translation file not uploaded yet
file uploaded but parse failed
book/chapter not found in imported dataset
chapter record exists but is empty and needs refresh
Use best practices for a production-ready import pipeline:
one focused parser/import path per translation if formatting differs
a shared normalization layer for book names and chapter detection
idempotent imports so re-uploading a corrected file updates existing records cleanly
no frontend secrets involved
robust handling for large text files
